PROJECT OVERVIEW
----------------
Task and Motion Planning (TAMP) for missions requiring a visibility-based device
with a field-of-view (FoV) -- a flashlight or camera -- rather than physical
contact with a target. Target platform: Ubuntu 18.04, ROS Melodic, a Husky
mobile base carrying a UR5 arm with a flashlight (conic FoV).

The material falls into three groups:

  (A) The research paper (LaTeX, in claude_context/) on Target Visibility Motion
      Planning (TVMP): the single-target-set problem solved by two new
      sampling-based planners, VisPRM and VisRRT. Being revised for RA-L.

  (B) Design notes (plain text, in claude_context/) for the next stage,
      Visibility TSP (VisTSP): observing MANY targets with the mobile
      manipulator.

  (C) The ROS package -- this repository. It implements Group A (the TVMP paper:
      VI-tree, VisIK, VisPRM, VisRRT, plus the VIR baseline) and its experiment
      harness. Of the Group B / global_plan.txt VisTSP components, steps 1 and 2
      exist -- the VI-tree multi-target query and the coverage query mode on
      both planners -- neither yet exercised by a real caller; see "VisTSP
      BACKLOG vs. CODE" at the end.

CURRENT STATE IN ONE LINE: the paper's planners are implemented, evaluated, and
running on hardware; the VisTSP extension has its VI-tree multi-target query and
its k-coverage planner queries written and compiling, and nothing yet consumes
them.

ARCHITECTURAL SHAPE -- read this before diving into files
---------------------------------------------------------
The package is almost entirely HEADER-ONLY. Every algorithm lives in a .h under
include/visual_based_planning/; src/visual_planner.cpp is a 3-line placeholder
that exists only so CMake has a library target. Consequence: when looking for an
implementation, look in include/, not src/. src/ holds only ROS nodes (executables)
and the CUDA kernels.

Runtime topology:
    visual_planning_node  (ROS service server "plan_visibility_path")
        owns -> PlanningContext   (shared_ptr; the world, outlives planners)
                  |-- ValidityChecker  (MoveIt collision + interpolation)
                  |-- VisualIK         (visibility-aware IK, MoveIt setFromIK)
                  |-- Sampler          (C-space + workspace sampling)
                  |-- PathSmoother     (shortcutting)
                  |-- VisibilityOracle (FoV/occlusion queries, CUDA-backed)
                  |-- VisibilityIntegrity  (the VI-tree -- paper's contribution)
                  |-- VisibilityRoadmap    (clustering variant -- the VIR baseline)
        owns -> VisibilityPlannerBase  (swappable; one run's state)
                  |-- GraphManager + NearestNeighbor (roadmap storage + kNN)
                  \-- VisRRTPlanner | VisPRMPlanner  (chosen by PlannerFactory)
    clients: visual_planning_client (single query + execute)
             experiment_runner      (batch benchmark over 5 configurations)

--- include/visual_based_planning/planners/ ----------------------------------

  The planner stack, split out of the former monolithic VisualPlanner.h. The
  split line is ownership: PlanningContext owns the WORLD (expensive, shared,
  survives across queries), VisibilityPlannerBase owns ONE RUN (cheap, discarded
  freely), and each concrete planner owns only its search.

planners/PlanningContext.h  (~337 lines)
  Role: The world a planner plans in -- robot, scene, and visibility structures.
  Significance: Exists so that constructing a planner is CHEAP. Held by
    shared_ptr, so switching algorithms (or, in the VisTSP pipeline, running a
    local planner once per base location) reuses one already-built VI-tree
    instead of rebuilding it. Without this split every planner instance would
    own -- and pay to build -- its own tree.
  Contents:
    - Constructor: wires ValidityChecker -> VisualIK -> VisibilityOracle ->
      Sampler -> PathSmoother -> robot_state/FK lambda -> VisibilityIntegrity +
      VisibilityRoadmap, then initialize_visibility(false).
    - initialize_visibility(bool build_structure = true): pulls collision objects
      out of the MoveIt PlanningScene and pushes their AABBs into the oracle,
      validity checker and sampler. Handles shapes::BOX and shapes::SPHERE only
      (MESH is a TODO), and the BOX path ignores shape rotation. Builds the
      active visibility structure only when build_structure && the
      use_visibility_structure_ flag -- the constructor passes false because the
      beam/VI parameters are loaded AFTER construction, so building there would
      use defaults. The first setPlanningScene() is what actually builds it.
    - setPlanningScene(): swaps the scene and rebuilds the visibility structures.
      This is the expensive path, and it invalidates any held VI-tree node
      pointers.
    - sampleVisibilityRegion(): the VI-tree / VIR roadmap dispatch, selected by
      use_visibility_roadmap_ (default false = VI-tree).
    - queryMultiTarget(): the VI-tree's multi-target query, returning false when
      the VI-tree is not the active structure or was never built -- a caller
      must not read that as "no region sees these targets".
    - basePosition(q): the mobile base's (x,y) for a configuration, read from
      the group's first two variables. THE one place that assumption lives; see
      CROSS-CUTTING NOTE 7. Throws on a configuration too short to hold one,
      rather than answering (0,0) and putting the base at the world origin.
    - getCurrentJoints(): the robot's current configuration, used to seed a
      planner's default start.
    - solveFK(), the component accessors, and every context-level setter.
  Gotchas: members are PUBLIC (planners reach them as ctx_->sampler_-> etc.) --
    a deliberate but wide surface, worth tightening to accessors later.
    group_name_ defaults to "whole_robot" (9 DOF: 2 planar base + arm) with
    "manipulator" commented out; workspace_bounds_ is hardcoded in the
    constructor before config overrides it.

planners/VisibilityPlannerBase.h  (~700 lines)
  Role: Common base for the visibility planners: the state of ONE run, plus the
    primitives every algorithm is written in terms of.
  Significance: The abstraction the node and the factory talk to. Declares BOTH
    pure virtuals: `plan()` (single target, returns a path) and `planCoverage()`
    (many targets, returns a labelled vertex set). Also defines CoverageResult
    and IKGroupGuard at namespace scope.
  Contents:
    - Holds shared_ptr<PlanningContext> as ctx_, plus per-run state: graph_, nn_,
      root_id_, checked_vertices_, start_joint_values_, target_mes_,
      result_path_, rng_.
    - MULTI-TARGET COVERAGE (global_plan step 2), all shared by both planners:
      state targets_/coverage_k_/min_goal_separation_/locality_/coverage_, and
      the helpers beginCoverageRun (validate + reset + the unseeable-target
      warning), reportUnseeableTargets, sampleLocalUniform (uniform sample with
      the base drawn inside the locality disk), inLocality, recordVisibleTargets
      (the per-vertex test against every unsatisfied target, plus the VisIK
      snap), creditTarget, coverageComplete (recomputes deficits; the ONLY place
      they are refreshed), isReachable (virtual), pickUnsatisfiedTarget,
      logCoverageSummary. The two search LOOPS stay in the planners.
    - The coverage query's promise is "k configurations per target, reachable
      from the start". goals[t] holds CANDIDATES; reachability is evaluated when
      completeness is checked, because a roadmap vertex can be disconnected when
      found and connected later.
    - snap_fov_on_insert_ (default true) / snap_fov_on_scan_ (default false):
      whether the VisIK snap may run on a vertex being ADDED, and on one the
      graph already held. Separate because the scan can face thousands of
      pre-existing vertices at once. recordVisibleTargets takes the applicable
      one as an ARGUMENT -- only the call site knows which case it is.
    - Holds BOTH RRTParams and PRMParams. Deliberate: the strategies mix -- the
      base's own connectToGraph() primitive reads PRMParams
      (edge_validation_method, num_neighbors) while extend() reads RRTParams, so
      either planner can reach for either. (This slot used to be justified by
      VisRRG, which was dropped on 2026-08-26; the mixing is still real.)
    - attachScene() vs setPlanningScene(): attachScene only points nn_ at a
      scene (two assignments); setPlanningScene also rebuilds the context. The
      split exists because NearestNeighbor returns NO neighbours at all while it
      has no scene, so a freshly built planner must be attached -- but attaching
      must not cost a VI-tree rebuild.
    - Primitives: interpolate/distance/validateEdge/extend, addState, reset,
      computeTargetMES, connectToGraph, sampleVisibilityGoal (takes the target
      as an argument; the no-target overload uses target_mes_), finalizePath.
    - Forwarding setters so callers configure a planner through one object.
      setUseVisibilityIntegrity() also sets the context's structure flag, so
      guidance can never be on while the structure it queries was never built.

planners/VisRRTPlanner.h  (~270 lines)
  Role: Visibility RRT. Maps onto Alg. vis:rrt in claude_context/4_Method.tex.
  Contents: plan() -- RRT with (a) goal-biased sampling drawn from the visibility
    structure, (b) a per-node direct-visibility goal test via
    checkBallBeamVisibility, (c) a VisIK "snap" branch converting a well-placed
    POSITION into a target-facing CONFIGURATION. Wall-clock capped by time_cap_.
    snap_fov_on_insert_ (ctor arg, default true) gates the snap; with it off the
    algorithm degrades to a plain RRT that only succeeds on direct visibility.
    planCoverage() -- the same search asked the multi-target question: the
    goal-biased draw aims at one target still short of coverage, every new node
    goes through recordVisibleTargets, and the tree keeps growing until ALL
    targets are satisfied. isReachable() is overridden to `true`: the tree is
    rooted at root_id_ and every vertex is attached to one already in it, so the
    base class's per-goal BFS would rediscover a structural guarantee.
  NOTE (2026-08-30): plan()'s snap now VERIFIES with the oracle that the snapped
    configuration actually meets the visibility threshold before declaring
    success. It previously trusted VisualIK, which picks the viewing point from
    geometry alone and never consults the obstacles, so an occluded snap could
    be reported as a solution. Stav accepted that the RA-L benchmarks need a
    re-run because of this.
  Intended as a base for VisRRT variants.

planners/VisPRMPlanner.h  (~390 lines)
  Role: Visibility PRM. Maps onto Alg. vis:prm in claude_context/4_Method.tex.
  Contents: plan() uses the configured start, or samples a random valid one while
    rejecting the double-room interior box (0<x<2.25, |y|<2.25), then delegates
    to planFrom(). planFrom() builds/extends a roadmap that PERSISTS ACROSS
    service calls (the graph is not reset between queries -- this is what makes
    PRM's amortized cost low in the paper's results), scans existing nodes for
    visibility, samples goals via the visibility structure, and returns a
    Dijkstra path.
    planCoverage() -- scans what the roadmap ALREADY holds against all targets
    (with snap_fov_on_scan_), then alternates goal sampling for one unsatisfied
    target with roadmap expansion (with snap_fov_on_insert_). max_goals keeps its
    meaning -- a cap on how many goal configurations are HELD, since sampling
    them is expensive and past a handful the useful work is connecting the ones
    already found -- but is now counted PER TARGET, one shared budget being
    spent by whichever targets came up first. Note it should be >= the coverage
    k, or goal sampling stops before a target can be satisfied by it (roadmap
    expansion can still credit vertices, so it is a slowdown, not a wall).
    Goal samples are added even when they connect
    to nothing, since an isolated candidate becomes creditable once the roadmap
    grows around it. The graph is NOT reset and there is no guard against
    reusing it under a different constraint -- see the note below.
  Intended as a base for VisPRM variants.

planners/PlannerFactory.h  (~67 lines)
  Role: Maps a mode string to a planner instance.
  Significance: The single place a new planner is registered -- a new algorithm
    means one new file plus one branch here, with no change to the node. Note
    the VisTSP multi-target work does NOT add one: it extends the two existing
    planners rather than introducing a third (decision 2026-08-26).
  Contents: PlannerOptions (snap_fov_on_insert, snap_fov_on_scan,
    use_visibility_integrity, shortcutting, time_cap, RRTParams, PRMParams) and
    createPlanner(mode, ctx, opts). Both snap flags are applied to EVERY planner,
    not only VisRRT: VisPRM uses the snap inside planCoverage().
    Accepts exactly "VisRRT" and "VisPRM"; returns nullptr for anything
    else, which callers treat as fatal rather than falling back.
  Gotcha: the old node dispatched on `mode.find("PRM") != npos`, so unrecognised
    strings silently ran VisRRT. Matching is now exact.

components/ValidityChecker.h
  Role: All collision and metric primitives.
  Significance: Every state/edge check in the system funnels through here, so it
    dominates runtime.
  Contents: isValid() (MoveIt checkCollision on the "whole_robot" group -- NOTE
    the group name is hardcoded in this call, not taken from group_name_);
    interpolate() and distance() delegating to MoveIt JointModel so continuous
    vs. revolute vs. prismatic joints are handled correctly; validateEdge() with
    LINEAR and recursive BINARY_SEARCH modes; extend() (RRT steering, returns the
    last valid state before collision); isPointInObstacle() / isPointInWorkspace()
    over Boost.Geometry AABBs. The bottom half of the file is a large
    commented-out earlier version that logged every checked configuration.

components/Sampler.h
  Role: All sampling -- both C-space and workspace.
  Contents: sampleUniform() (MoveIt setToRandomPositions on the group);
    sampleValidPoints() (uniform workspace points, plus optional "face sampling"
    that seeds points just outside each obstacle face by 5 mm -- used by the
    visibility roadmap); sampleInBox() (collision-free points in an AABB, the
    VI-tree's S_in); sampleOutside() (points in B but outside B', optionally
    limited to a `range` band around B' -- the VI-tree's S_out, where range is
    the beam length); computeLookAtRotation() (builds the camera frame whose +Z
    points at the target); two sampleVisibilityAwareState() overloads (ball
    target and point-set target) that grow the sampling radius geometrically
    until an IK-feasible, sufficiently-visible pose is found.

components/VisualIK.h
  Role: Visibility-aware inverse kinematics -- the paper's VisIK
    (4_Method.tex, sec:method:vis:ik).
  Significance: The component that turns "this place can see the target" into
    "this joint configuration sees the target".
  Contents: solveIK() (plain MoveIt setFromIK with a ValidityChecker callback);
    solveVisualIK(current_joints, Ball, orientation, out) -- the core: from beam
    half-angle theta and length h it computes the feasible standoff segment
    [a,b] along the view axis (near bound r/tan(theta), far bound h-r), clips
    that segment against a reachability AABB via the slab method, projects the
    current EE position onto it, and then does a bidirectional local search
    along the segment calling IK at each step; overloads for a point list;
    maintainOrientationVisualIK() (keep current EE orientation);
    greedyOrientationVisualIK() (recompute a look-at orientation first).
  TWO GROUPS (2026-08-30): the STATE group (setGroupName) says what a
    configuration vector means -- what seeds are expressed in, what FK is read
    from, what solutions are returned in. The IK group (setIKGroupName) says
    which of those joints the solver may MOVE, defaulting to the state group.
    Set to "manipulator" while a base-locality constraint is active, so a
    solution inherits its seed's base position and cannot leave the disk;
    joints outside the IK group keep their seed values, so inputs and outputs
    stay full state-group vectors either way. checkIK's validity callback
    applies the candidate to the state and reads the FULL state-group vector
    back before collision checking -- with a subgroup, handing ValidityChecker
    the group's own values would pass 6 numbers to a 9-variable group.
    IKGroupGuard (VisibilityPlannerBase.h) is what scopes the restriction: this
    object is shared through PlanningContext, so an unrestored setting would
    leave every later query solving arm-only.
  Known issues, marked in-file with @todo: the search direction/step-size logic
    is flagged WRONG by the author ("dir should be equal to v, step size should
    differ per direction"), and there is a commented-out hard-coded flashlight
    offset. The clipping AABB (-5,-5,0)..(5,5,1.4) is hardcoded here.

components/PathSmoother.h
  Role: Path post-processing (the `enable_shortcutting` option).
  Contents: smoothPath() -- exact shortcutting by dynamic programming: treats the
    waypoints as a DAG, edge i->j exists if validateEdge succeeds, and takes the
    minimum-cost chain. Not randomized shortcutting; it is optimal over the given
    waypoint set but costs O(n^2) edge checks.

components/PathExecuter.h
  Role: Sends a joint-space path to the real/simulated robot.
  Significance: The only file that talks to MoveGroupInterface for execution;
    used by visual_planning_client, not by the planner service.
  Contents: builds a RobotTrajectory, runs IterativeParabolicTimeParameterization
    with velocity/acceleration scaling (defaults 0.025 / 0.05 -- deliberately
    slow), then execute(). A `wait_time > 0` debug mode instead moves waypoint by
    waypoint with a 2 s pause between each (useful for watching the FoV).

data_structures/VisibilityIntegrity.h  (the VI-TREE -- key contribution)
  Role: Implements the Visibility Integrity tree from 4_Method.tex
    (sec:method:visibility:integrity:tree; Algs. vi:tree, vi:tree:recursive,
    vi:tree:query).
  Significance: This is the paper's headline data structure. It answers "which
    regions of the workspace can see this target?" without per-query raycasting.
  Contents:
    - struct VINode: AABB, left/right/parent, is_leaf, height, path_idx string
      (e.g. "0101" for debugging), convexity_score, and
      visible_from_nodes: vector<(VINode*, score)> -- the inverse-visibility list.
    - build(): recursive AABB partition, then ComputeLeafPairwiseVisibility(),
      then ComputeParentVisibilityBottomUp().
    - buildTreeRecursive(): samples S_in inside the box (count scaled down with
      box volume) and S_out in the environment around it (within beam_length),
      uploads the combined set to the GPU as one NxN visibility matrix
      (precomputeGpuMatrix), then computes the VI score as
      |{S_out seen by ALL of S_in}| / |{S_out seen by ANY of S_in}| using the
      checkSeenByAll/Any reduction kernels. Splits on the longest axis while the
      score is below vi_threshold; makes a leaf when the score passes or the box
      shrinks below 0.1 m. Also derives a convexity_score from the same data.
    - ComputeLeafPairwiseVisibility(): one all-pairs GPU batch over leaf centers.
    - ComputeParentVisibilityBottomUp(): a parent's visibility list is the
      INTERSECTION of its children's (sorted-merge), with the score averaged, and
      the relation is written back into the seer's list so queries at any depth
      work. Single-child nodes copy and propagate.
    - query(Eigen::Vector3d, out): descends to the containing leaf, accumulating
      visible_from_nodes from every ancestor on the path.
    - query(Ball, out): the version actually used -- traverses, prunes boxes
      outside the ball, and accumulates a per-seer BALL FRACTION. The covering
      nodes (fully-contained nodes, where recursion stops, plus partially
      intersecting leaves) form a disjoint cover of the ball, so their fractions
      can be summed: each seer's score is the dimensionless fraction of the target
      ball visible from it, in [0,1].
    - query(vector<Ball>, MultiTargetQueryResult&, threshold = 0.8): the
      MULTI-TARGET query (VisTSP subproblem 1, global_plan step 1). Runs the
      single-ball query per target, keeps the seers whose accumulated ball
      fraction is >= threshold, and fills the relation in BOTH directions:
      per_target[t] (regions -> fraction) and region_to_targets (region ->
      target indices). Both are needed because pruning walks regions but
      validates per target. Warns on any target left with no region -- the
      signal that the threshold is stricter than the score distribution allows.
      Per-target fractions are accumulated independently: they may only be
      summed within one target, where the covering nodes form a disjoint cover.
      Seers are returned at ALL tree levels, nested ones included -- collapsing
      to the highest-level node was considered and rejected, because the
      per-node scores record how well each part of a subtree sees the target and
      that resolution would be lost.
      Its first caller (2026-08-30) is VisibilityPlannerBase::
      reportUnseeableTargets, reached through PlanningContext::queryMultiTarget:
      a warning that a target no region sees cannot be covered however long the
      search runs. Advisory only -- a region's score is an aggregate over the
      region, so passing does not promise any single configuration in it sees
      the target.
    - isBuilt(): whether build() has produced a tree. Every query answers
      emptily until it has, which a caller cannot otherwise tell apart from
      "nothing sees the target".
    - Sparse accumulator (accum_ + touched_): the ball query sums each seer's
      fractions through a flat vector indexed by node id rather than a linear
      scan over the output, turning O(covering * list * seers) into
      O(covering * list). Node ids are dense (0 .. num_nodes_-1, sized in
      build()). INVARIANT: accum_ is all zeros between queries -- each query
      resets only the entries in touched_, so cost stays proportional to the
      seers actually hit, and one buffer serves every target of a multi-target
      query. The zero entry doubles as the "not yet credited" marker, which is
      only sound because ball_fraction is strictly positive there.
    - SampleFromVisibilityRegion(Ball, out_point, threshold): rejection sampling
      -- pick a seer, accept it with probability (its ball fraction / the max ball
      fraction over all seers), sample a collision-free point in its box, and
      confirm with a real checkBallBeamVisibility call. The rescale by the max is
      deliberate: raw fractions are usually well below 1 (a seer rarely covers a
      whole target), so using them directly would reject nearly every candidate.
      Dividing by the max preserves the relative ranking -- all that rejection
      sampling needs -- while keeping the best candidate's acceptance rate at 1.
    - Geometry helpers: distSqPointBox, distSqBoxBox, isBoxFullyInBall,
      getBoxVolume/Size, getBallVolume, getIntersectionVolume (raw m^3 of
      box n ball; exact when the box is fully inside, Monte-Carlo otherwise),
      getBallFraction (= getIntersectionVolume / getBallVolume). getBallFraction
      is the SINGLE normalization point -- both the fully-contained and the
      partial case go through it, so scores stay comparable across nodes.
  Gotchas: makeLeaf() APPENDS every leaf to "leaf_boxes.txt" in the process CWD
    (usually ~/.ros) on every build -- a debug/visualization dump that grows
    across runs. intersectsWorkspaceBox() hardcodes the reachable goal AABB
    (-5,-5,0)..(5,5,1.4); intersectsWorkspaceSphere() is an unused alternative
    with a hardcoded 1.2 m sphere at (0.33, 0, 0.33).

data_structures/VisibilityRoadmap.h
  Role: The ALTERNATIVE to the VI-tree: a clustering-based visibility structure.
    Selected by use_visibility_roadmap:=true. This is the "VIR" configuration in
    experiment_runner -- i.e. the Visibility Roadmap BASELINE from
    2_Related_work.tex, not a contribution.
  Significance: Same public query surface as VisibilityIntegrity
    (SampleFromVisibilityRegion, query, isConnectedToTarget), so PlanningContext
    can swap one for the other behind a single boolean.
  Contents: build() = sample N valid workspace points (with optional face
    sampling) -> computeSampleVisibility (all-pairs, GPU with a CPU fallback,
    stored as sorted adjacency lists) -> performClustering() ->
    buildClusterVisibilityGraph() -> build a kNN index over the samples.
    Clustering is greedy: seed on a random point, walk outward by distance, admit
    a point while the incremental VI score (|intersection of visibility sets| /
    |union|) stays >= vi_threshold, stop when the diameter exceeds
    limit_diameter_factor * current diameter. Each cluster gets a centroid and a
    bounding radius. The cluster graph gets an edge when random member pairs are
    mutually visible, weighted by the observed fraction, and is pruned to
    clusters intersecting the goal AABB. query() classifies a point by kNN
    majority vote over cluster labels. Prints extensive cluster statistics and
    dumps "clustered_points.txt".
  Gotcha: goal AABB (-5,-5,0)..(5,5,1.4) is hardcoded again here.

data_structures/VisibilityOracle.h
  Role: All visibility/FoV queries. The CPU-side API over the CUDA kernels.
  Significance: The performance-critical core; every planner decision is
    ultimately an oracle call.
  Contents:
    - Obstacle store as Boost.Geometry Box3D, mirrored to GPU lazily via a
      gpu_dirty_ flag (updateGPUObstacles).
    - isPointInFOV(): the cone test -- transform the target into the sensor
      frame, require +Z half-space, distance <= beam_length, and
      cos(angle) >= cos(beam_angle).
    - isPointInBeam() = isPointInFOV && unoccluded segment.
    - ballOutsideBeam(): closed-form rejection of a ball ENTIRELY outside the
      beam, run first thing inside checkBallBeamVisibility. A ball only
      partially inside is never rejected: for a sensor outside it, the
      directions to its points fill exactly the tangent cone of half-angle
      asin(r/d), and two cones are disjoint only when their axes differ by more
      than the sum of their half-angles. Where it fires, the sampling loop would
      have found nothing in the field of view and returned 0.0, so it changes
      cost and not results. Added for the multi-target coverage queries, which
      test every vertex against every uncovered target.
    - checkBallBeamVisibility(): the central scoring function -- Monte-Carlo
      samples num_samples_ (100) points in the target ball and returns the
      illuminated fraction. Overloads take an Isometry3d pose, a joint vector
      (via the injected FK lambda), or a bare source position (in which case a
      look-at frame is synthesized). NOTE: the GPU batch branch inside this
      function is disabled by `if (false)` -- it always runs the CPU path.
    - computeBatchVisibility(): all-pairs NxN on GPU.
    - checkBatchVisibility(): a list of specific segments on GPU.
    - precomputeGpuMatrix() + checkSeenByAllGPU() / checkSeenByAnyGPU(): upload
      an NxN matrix once and run cheap index-only reductions against it -- this
      is what makes VI-tree construction tractable.
    - VisibilityMethod enum {BF, GPUBF, KDTree}; default GPUBF; KDTree throws.

data_structures/VisibilityOracleGPU.h
  Role: The C/CUDA boundary -- POD structs and kernel launcher declarations, free
    of Boost/Eigen so the .cu file can include it.
  Contents: struct GPUBox, struct GPUPoint; declarations of
    launchVisibilityKernel, launchAllPairsVisibilityKernel,
    launchBatchSegmentKernel, launchComputeSeenByAll, launchComputeSeenByAny.

data_structures/Graph.h
  Role: Roadmap/tree storage and graph algorithms (namespace-free; class
    GraphManager).
  Contents: Boost adjacency_list<vecS, vecS, undirectedS> with GraphVertex
    {joint_config, ee_pose} and GraphEdge {weight}; addVertex/addEdge (note:
    addEdge inserts BOTH directions into an already-undirected graph, so each
    logical edge appears twice); getVertexConfig/getVertexPose; isEdge;
    shortestPath (Boost Dijkstra + backtracking); inSameComponent (BFS with early
    exit -- used as a cheap pre-check before Dijkstra); countConnectedComponents
    (prints the k largest with a representative config); exportCCMap() (writes
    cc_map.txt: id, joint values, connected-component id -- for offline analysis
    of why PRM failed to connect); printVertexDegrees.

data_structures/NearestNeighbor.h
  Role: kNN over configurations, with a robot-aware metric.
  Significance: Contains a real performance trap -- see below.
  Contents: PointCloud adaptor; RobotStateDistance metric that uses MoveIt
    JointModel::distance per joint and then WEIGHTS the dimensions -- prismatic
    joints (the Husky base translations) by the DOF count, revolute joints by
    (n - i) so proximal arm joints dominate distal ones. This weighting is what
    makes nearest-neighbour queries prefer moving the arm over driving the base.
    Wraps nanoflann KDTreeSingleIndexAdaptor; also provides bruteForceKNN.
  Gotcha: addPoint() DELETES AND REBUILDS the entire kd-tree on every insertion,
    making roadmap construction O(n^2 log n). This is the most likely target if
    PRM build time needs to come down (cf. commit "trying to make NN faster").

data_structures/nanoflann.hpp
  Role: Vendored third-party header (nanoflann kd-tree). Do not edit.

src/visual_planning_node.cpp
  Role: The main ROS service node -- the production entry point.
  Contents: class VisualPlanningNode wraps a PlanningSceneMonitor, one shared
    PlanningContext, and a swappable VisibilityPlannerBase, and advertises
    "plan_visibility_path".
    - loadStaticConfig(): reads every parameter from the PRIVATE namespace
      (planner_config.yaml). Context-level values go straight to ctx_;
      planner-level ones (RRT/PRM params, time cap, snap_fov_on_insert,
      snap_fov_on_scan) are RETAINED as members so a rebuilt planner can be
      configured identically. First calls rejectRetiredParams(), which REFUSES
      TO START if a config still sets a renamed parameter (currently
      use_visual_ik -> snap_fov_on_insert): ROS reports nothing for a parameter
      nobody reads, so the run would silently take the new default and, for this
      one, benchmark the wrong algorithm.
    - rebuildPlanner(scene, mode): builds the planner named by mode on the
      existing context and attachScene()s it. Cheap -- no VI-tree rebuild.
      Returns false on an unknown mode; the constructor treats that as fatal and
      a request treats it as a failed request. There is deliberately NO fallback
      to a default planner.
    - updatePlannerParams(): on EVERY service call, re-reads five switches from
      the GLOBAL namespace (/planner/snap_fov_on_insert,
      /planner/snap_fov_on_scan, /planner/use_visibility_integrity,
      /planner/use_visibility_roadmap, /planner/enable_shortcutting, planner/mode)
      and sets params_changed_ if any differ. This is the mechanism
      experiment_runner uses to switch algorithms without restarting the node.
    - planCallback(): resolves the mode (req.planner_type overrides the param
      server for that call only); if the CONTEXT is uninitialized OR params
      changed, resets the planner and re-snapshots the scene (this is what
      triggers the VI-tree rebuild); rebuilds the PLANNER if the mode differs
      from the one built or a construction-time flag changed; then computes the
      target MES and start joints -- in that order, because both are per-run
      state that a rebuild would discard -- calls plan(), and packs the result
      into a JointTrajectory with the group's active joint names.
    - main(): RobotModelLoader + PlanningSceneMonitor with scene/world/state
      monitors, AsyncSpinner(2).

src/visual_planning_client.cpp
  Role: Single-query client: request a plan and execute it on the robot.
  Contents: resolves the planner mode (private ~mode -> /visual_planning_node/
    planner/mode -> "VisRRT" default); reads the flat /target_points array

src/experiment_runner.cpp
  Role: The benchmark harness that produced the paper's numbers.
  Significance: The single best file for understanding the experimental protocol
    in claude_context/5_Experiments.tex.
  Contents:
    - Five configurations compared, each a (mode, snap_fov_on_insert,
      use_visibility_integrity, use_visibility_roadmap) tuple:
        VisRRT (VisRRT + VisIK), RRT (plain), VisPRM (PRM + VI-tree),
        VIR (PRM + visibility roadmap = the baseline), PRM (plain).
      Switched at runtime by setting the global /planner/* params. The table is
      positionally initialised, so the 2026-08-30 rename of use_visual_ik cost
      it no edit; /planner/snap_fov_on_scan is pinned false per run so a run
      cannot inherit it from the previous one.
    - generateTargetProblemsFromRegions(): loads sampling_regions_double_room.yaml,
      pulls the real obstacle AABBs out of the live MoveIt planning scene, and
      pre-generates 200 target problems -- each a sphere sampled inside a region
      with the largest radius that fits, rejected if it intersects any obstacle,
      then populated with 100 uniformly-distributed interior points.
    - 200 trials per configuration; trial 0 is recorded separately as the
      initialization/build cost (the amortization argument in the paper).
    - computeStats (avg/median/min/max/stddev), printStats, saveToFile ->
      planner_experiments_results.txt, including per-run success flags and a
      per-target room flag (x>0 = "windows" room, x<0 = "door" room).
  Bug worth knowing: room_flags_ is only `reserve`d, never `resize`d, but is
    written via `room_flags_[i] = ...` -- out-of-bounds writes to a vector of
    size 0. The room column in saved results is therefore unreliable.

CROSS-CUTTING NOTES (things that will bite you)
-----------------------------------------------
1. "whole_robot" vs "manipulator": the planning group was switched from the UR5
   alone to the full 9-DOF mobile manipulator. The old value survives as
   commented-out lines in the planners/ headers, ValidityChecker.h, NearestNeighbor.h,
   visual_ik_server.cpp, visual_ik_client.cpp, visual_planning_client.cpp.
   ValidityChecker::isValid() still hardcodes "whole_robot" in its
   getJointModelGroup call rather than using group_name_.
2. The reachable/goal AABB (-5,-5,0)..(5,5,1.4) is hardcoded in THREE places:
   VisibilityIntegrity::intersectsWorkspaceBox, VisibilityRoadmap::
   buildClusterVisibilityGraph, and VisualIK::solveVisualIK. Changing the
   environment means changing all three.
3. Debug artifacts are written to the process CWD (~/.ros when launched by
   roslaunch): leaf_boxes.txt (appended, grows unboundedly), clustered_points.txt,
   cc_map.txt.
4. The CUDA arch flag is pinned to sm_89 in CMakeLists.txt.
5. VisibilityOracle::checkBallBeamVisibility's GPU branch is dead code
   (`if (false)`); ball visibility scoring is CPU-bound.
6. The PRM roadmap deliberately PERSISTS across service calls; only a param
   change or scene change resets it. Timing numbers only make sense in that light.
7. TARGET ROBOTS ARE EXACTLY TWO (Stav, 2026-08-30): the SIMULATED mobile UR5,
   whose base x/y are prismatic joints anchored to the centre of the
   environment, and the REAL Husky + UR5. Nothing else -- no other robot,
   simulated or otherwise, needs to be supported. Generality is explicitly worth
   trading away for simpler code here. Concretely, the first two variables of
   the planning group ARE the base translation, and code may rely on it.
   Where the base is gets asked through PlanningContext::basePosition() so that
   the real Husky, which will report its base from localization rather than
   from a joint value, changes one method (or backs it with a ROS service)
   instead of every caller.
   OPEN RISK on the real Husky, flagged by Stav as untried (2026-08-30), and
   UNVERIFIED against their setup:
   (a) Getting the base position may not need new code at all. If the Husky's
       base is a PLANAR VIRTUAL JOINT (map -> base_link) inside the planning
       group, q[0]/q[1] stay the base translation and PlanningSceneMonitor
       already fills the current state from TF; the work is then SRDF plus a
       localization source, not C++. basePosition() only has to change if the
       base ends up OUTSIDE the planning group.
   (b) The harder problem is that a Husky is DIFFERENTIAL-DRIVE while the
       simulated base is two prismatic joints, which slide sideways. Every base
       path this code plans is therefore a relaxation the real robot may not be
       able to execute. Under a small locality disk the base barely moves so it
       is minor; for the global tour over base locations (global_plan step 6) it
       is not, and nothing in the repo addresses it yet.
8. ONE PLANNER PER REGION is the contract for the VisTSP pipeline (Stav,
   2026-08-30). Whenever a graph is needed -- local or global -- construct a
   planner and take its graph; each local region gets its own, because each
   region's tour is computed from its own graph. This is why the base-locality
   constraint needs no guard against a roadmap built under a different disk:
   there is no shared mutating roadmap to protect. Reusing one planner with a
   LARGER delta is legitimate, its vertices all still being inside, and
   shrinking one is the caller's business -- recordVisibleTargets tests
   inLocality on the vertex it is given, so the answer stays correct either way.
   A freshly constructed planner must be attachScene()d before it can plan.

global_plan.txt
  Role: The project's global plan. DO NOT EDIT (CLAUDE.md item 4).
  Contents: implement VisTSP (search/illuminate/film a SET of targets), via a
    6-step ordered task list: (1) multi-target query for the VI-tree,
    (2) multi-target queries for VisRRT and VisPRM, (3) "Greek TSP" algorithm,
    (4) LocalVisTSP,
    (5) covering algorithm (cover regions with copies of the reachable volume),
    (6) TSP over the 2D base locations. Steps 1-4 are the LOCAL pipeline,
    5-6 the GLOBAL pipeline; together they are the GLVisTSP framework.
  SUPERSEDED STEP 2 (Stav's decision, 2026-08-26): VisRRG will NOT be
    implemented. Step 2 is instead a MULTI-TARGET QUERY MODE for the existing
    VisRRT and VisPRM, taking a set of target balls plus an optional COVERAGE
    parameter k -- the number of reachable configurations that must see each
    target. This is step 1 of the VisCfgTSP framework in VisTSP_frameworks.txt
    ("configurations s.t. every target is watched by at least K configurations")
    and it feeds the same downstream steps VisRRG would have fed. Reusing the
    two planners also keeps one code path per algorithm instead of a third.
    Stav updated global_plan.txt himself on 2026-08-30 to match; that file is
    his alone to edit (CLAUDE.md item 4), and this entry carries the reasoning
    the one-line plan has no room for.
  STEP 2 ALSO INCLUDES an OPTIONAL LOCALITY CONSTRAINT (same decision): the
    multi-target query may cap how far the mobile base travels. The constraint
    is a DISK -- the base stays within delta of the ROOT configuration's base
    position -- not the axis-aligned box B of local_VisTSP.txt. This is what
    makes the same query serve as the "local" planner of LocalVisTSP (step 4),
    where subproblem 3 requires the base within delta of a location, so no
    separate local planner is needed. delta is optional: unset means the
    unconstrained multi-target query.
  VisIK UNDER THE LOCALITY CONSTRAINT (decision NOT final, revisit if a better
    option appears): call VisIK on the "manipulator" group instead of
    "whole_robot", so the solver cannot move the base at all. Rationale: IK over
    whole_robot is free to place the base anywhere in its joint range, so a snap
    can silently leave the disk; solving arm-only makes the constraint hold by
    construction for every snapped configuration. Cost: less IK freedom, so
    targets reachable only by shifting the base slightly are not snapped -- they
    have to be covered from a different node whose base the SAMPLER moved (which
    stays inside the disk anyway). The alternative left on the table is
    whole_robot IK with a disk validity callback on setFromIK: more freedom, but
    it relies on random seed restarts to land inside the disk.

  Contents: Local VisRRG(r, E, B, T, k) -- sample the VI-tree for target configs,

    VisIK, all within a local bounding box B; "TSP Greek Alg" -- MST -> post-order

    shortcut is hard (the interesting case); LocalVisTSP = Local VisRRG then
    GreekTSP.

    labelled goal configurations instead. What survives unchanged is the ROLE
    that structure plays: the k-per-target coverage requirement, the locality
    constraint (as a DISK, see below, not the box B), and the GreekTSP half,
    which still consumes a graph plus per-target goal vertices.

The building blocks are in place for step 3: both planners now hand back a graph
plus per-target goal vertices, which is what a tour needs. Everything else in the
repo serves the TVMP paper (single target set). The
building blocks the VisTSP steps will reuse are: VisibilityIntegrity (both
queries + SampleFromVisibilityRegion), VisualIK, VisibilityOracle (especially
the cached GPU matrix + seen-by-all/any reductions), Sampler, GraphManager,
ValidityChecker -- and now PlanningContext, which is what lets a per-location
local planner share one built VI-tree.


HOW THE PIECES RELATE
---------------------
The paper (Part 2, Group A) defines the primitives -- the VI measure, the VI-tree,
VisIK, and the VisPRM/VisRRT planners for single-goal TVMP. Part 1 (the repo) is
their implementation on the Husky + UR5, together with the VIR baseline and the
benchmark harness that produced 5_Experiments.tex. The VisTSP notes (Part 2,
Group B) reuse those same primitives -- above all the VI-tree query and VisIK --
to build multi-target coverage: regions from the VI-tree, base locations covering
those regions, a global tour over locations, and local visibility tours at each
stop. global_plan.txt sequences that into 6 build steps, of which only step 1 is
written (Part 3). The reuse is now literal rather than conceptual: as of
2026-08-26 the local coverage stage is not a new planner but a multi-target,
k-coverage, base-locality-constrained query mode ON VisRRT and VisPRM
themselves.
