PROJECT OVERVIEW
----------------
Task and Motion Planning (TAMP) for missions requiring a visibility-based device
with a field-of-view (FoV) -- a flashlight or camera -- rather than physical
contact with a target. Target platform: Ubuntu 18.04, ROS Melodic, a Husky
mobile base carrying a UR5 arm with a flashlight (conic FoV).

The material falls into three groups:

  (A) The research paper (LaTeX, in claude_context/) on Target Visibility Motion
      Planning (TVMP): the single-target-set problem solved by two new
      sampling-based planners, VisPRM and VisRRT. Being revised for RA-L.

  (B) Design notes (plain text, in claude_context/) for the next stage,
      Visibility TSP (VisTSP): observing MANY targets with the mobile
      manipulator -- now including the reference material and implementation
      plan for the GTSP heuristics of step 3.

  (C) The ROS package -- this repository. It implements Group A (the TVMP paper:
      VI-tree, VisIK, VisPRM, VisRRT, plus the VIR baseline) and its experiment
      harness. Of the Group B / global_plan.txt VisTSP components, steps 1 and 2
      exist -- the VI-tree multi-target query and the coverage query mode on
      both planners -- neither yet exercised by a real caller; see "VisTSP
      BACKLOG vs. CODE" at the end.

CURRENT STATE IN ONE LINE: the paper's planners are implemented, evaluated, and
running on hardware; the VisTSP extension has its VI-tree multi-target query and
its k-coverage planner queries written and compiling, and nothing yet consumes
them.

ARCHITECTURAL SHAPE -- read this before diving into files
---------------------------------------------------------
The package is almost entirely HEADER-ONLY. Every algorithm lives in a .h under
include/visual_based_planning/; src/visual_planner.cpp is a 3-line placeholder
that exists only so CMake has a library target. Consequence: when looking for an
implementation, look in include/, not src/. src/ holds only ROS nodes (executables)
and the CUDA kernels.

Runtime topology:
    visual_planning_node  (ROS service server "plan_visibility_path")
        owns -> PlanningContext   (shared_ptr; the world, outlives planners)
                  |-- ValidityChecker  (MoveIt collision + interpolation)
                  |-- VisualIK         (visibility-aware IK, MoveIt setFromIK)
                  |-- Sampler          (C-space + workspace sampling)
                  |-- PathSmoother     (shortcutting)
                  |-- VisibilityOracle (FoV/occlusion queries, CUDA-backed)
                  |-- VisibilityIntegrity  (the VI-tree -- paper's contribution)
                  |-- VisibilityRoadmap    (clustering variant -- the VIR baseline)
        owns -> VisibilityPlannerBase  (swappable; one run's state)
                  |-- GraphManager + NearestNeighbor (roadmap storage + kNN)
                  \-- VisRRTPlanner | VisPRMPlanner  (chosen by PlannerFactory)
    clients: visual_planning_client (single query + execute)
             experiment_runner      (batch benchmark over 5 configurations)

src/vistsp_experiment_runner.cpp  (~800 lines, NEW 2026-09-09)
  Role: Experiment driver for the VisTSP additions (global_plan steps 3-4).
    Samples target spheres from the workspace regions, then evaluates one or
    more tour METHODS on the same problem set.
  Significance: this is where the "what do the extra layers buy" comparison
    will be measured. src/experiment_runner.cpp (the TVMP paper's driver) is
    left untouched.
  Kept from experiment_runner.cpp, deliberately: problems are PRE-GENERATED
    ONCE and reused by every method, which is what makes the comparison PAIRED
    and therefore meaningful; region sampling; radius = shortest distance to the
    region bounds; rejecting a sphere that intersects a scene obstacle; params
    set between configurations with a settle; the stats block.
  Changed: a TRIAL IS A SET OF M TARGETS, not one. Regions are drawn WITH
    REPETITION within a trial (Stav's spec), so two targets can land in one
    region and may OVERLAP -- flagged in TourProblem::has_overlap and carried
    into the CSV rather than prevented, because an overlap is exactly the case
    where one configuration sees two targets and is therefore what exercises
    node splitting (D3) and RP1's candidate sets. No point clouds are sampled:
    the tour service takes spheres directly. room_flags_ is gone -- "which
    room" is not one bit when a trial has M targets -- replaced by the per-
    target region_id.
  NO CONFIG PER INSERTION RULE, AND NONE FOR 2-OPT ON/OFF. One tour call
    returns every enabled rule's cost before AND after 2-opt, so a row per rule
    would re-run the expensive coverage query to learn what one call already
    reports. Configurations vary only what genuinely needs a separate run: the
    planner mode, the coverage k, and base locality.
  HOW GlobalVisTSP PLUGS IN (Stav asked for this explicitly): TourProblem and
    TrialOutcome mention no method, and the stats, printing and file output
    touch only TrialOutcome. Exactly ONE function is method-specific,
    callMethod(). Adding GlobalVisTSP is one more MethodConfig row plus one
    branch there -- generation and reporting do not change, and both methods
    are then automatically compared on the same problem set.
  Markers: behind ~publish_markers (default true). A translucent SPHERE at each
    target's true radius plus a TEXT label with the target INDEX -- the labels
    matter because the response's stop_target refers to those indices, so
    without them a tour cannot be read off the screen. A DELETEALL is sent
    first so the previous trial's markers are not mistaken for this one's.
  Gotcha: the marker frame comes from the ROBOT MODEL
    (RobotModelLoader::getModel()->getModelFrame()), which is the planning
    frame the collision objects are expressed in. PlanningSceneInterface has NO
    getPlanningFrame() in Melodic -- assuming it did was a compile error. Since
    2026-09-16 the model is loaded ONCE by loadRobotModel() and shared with the
    start-state resolution, and failing to load it is now FATAL rather than
    just disabling markers: without the model there is no start configuration
    either.
  DELEGATES TO common/RunSetup.h since 2026-09-17: the region load, the scene
    read and wait, the draw, the start state, the parking and the markers all
    moved there so the tour client performs them identically. The runner keeps its
    trial structure, its statistics and its reporting - what moved is only the
    setup, and the RNG order is unchanged, so an old seed still reproduces its old
    problem set.
  START CONFIGURATION (2026-09-16, Stav's request). run() is now
    waitForExistence -> loadRobotModel -> resolveStartState -> parkRobot ->
    loadRegions -> waitForScene -> loadObstacles -> generateProblems.
    - resolveStartState() turns ~start_state (default "vertical") into the joint
      vector sent as PlanVisibilityTour's start_joints on EVERY trial of EVERY
      method. A NAMED SRDF group_state, never a vector in YAML: "whole_robot" is
      built from subgroups, so a hand-written list would depend on MoveIt's
      variable order. Resolving it through RobotState::setToDefaultValues +
      copyJointGroupPositions uses the same order the node's applyStartJoints()
      does, by construction. An unknown name is FATAL and lists the known states
      (fail-loud: falling back to the current state would still produce numbers).
      An explicitly empty ~start_state keeps the old "use the robot's current
      state" behaviour and warns that it is not reproducible.
    - The group comes from ~planning_group, else from the NODE's
      /visual_planning_node/planner/group_name, so planner_config.yaml stays the
      single authority; neither set is a refusal, not a default.
    - parkRobot() publishes that state to /move_group/fake_controller_joint_states
      (demo.launch's joint_state_publisher source_list), so RViz and the scene's
      current state agree with what is planned from. Simulation only; with no
      subscriber it warns and continues, because the request carries the start
      explicitly anyway. Not purely cosmetic: ValidityChecker works on the
      scene's current state, which the context snapshots on the first request.
    - waitForScene() blocks until the scene holds ~min_scene_objects objects
      (default 1, ~scene_wait_timeout default 120 s) and REFUSES to run
      otherwise. An empty world has no occlusion, so every target is trivially
      visible: the experiment would still produce a full results file. It runs
      BEFORE generateProblems() because obstacles decide which sampled targets
      are rejected.
    - The results header now records the start state and the obstacle count, so
      a results file says which world and which start produced it.
  Output: <results_prefix>.txt (human readable, per-phase timing and cost) and
    .csv (one row per method/trial/rule, including has_overlap -- plot from
    this one).
  ~rng_seed defaults to a FIXED value so the problem set is reproducible across
    invocations, not just within one run.
  Status: written and syntax-checked; NOT yet run.

src/visual_planning_tour_client.cpp  (~520 lines, NEW 2026-09-09,
                                      execution + sampling 2026-09-17)
  Role: ONE VisTSP run: get the targets, call the service, print the cost table,
    draw the targets and the tour, and RUN IT ON THE ROBOT.
  Significance: the single-run counterpart of the experiment runner. The runner
    answers "how do these methods compare over many problems" and executes
    nothing; this answers "what does one run look like" and executes it.
  TARGETS COME FROM EXACTLY ONE OF: ~sampling_regions_file (a random draw, with
    ~num_targets/~rng_seed/~max_target_radius, through common/RunSetup.h's
    TargetSampler - so a given seed reproduces the experiment's trial 0), or
    ~targets_yaml (fixed targets, three shapes, below). Both set, or neither, is
    REFUSED: a launch file that sets both means one of them is not doing what its
    author thinks.
  EXECUTION: ~execute (default true) runs the returned trajectory through
    PathExecuter on the group the NODE planned for, the same component the
    single-target client uses; ~velocity_scaling / ~acceleration_scaling throttle
    it. The robot is parked at ~start_state (default "vertical") first, so
    execution starts where the tour was planned from instead of jumping there. An
    AsyncSpinner runs before PathExecuter is built, since MoveGroupInterface waits
    on callbacks.
  DRAWING: the targets go out before the service call, so they are on screen while
    the coverage query runs; drawTour() then publishes the END EFFECTOR's path
    through the whole trajectory as a LINE_STRIP plus a labelled marker per stop
    ("stop 2 -> target 0"), the tour being a configuration-space cycle that cannot
    be drawn directly. Decoration, so every failure in it warns and returns.
    Topics ~vistsp_targets and ~vistsp_tour, both latched, both displayed by
    config/vistsp_experiments.rviz.
  Significance: THE PLACE CLOUD-TO-SPHERE CONVERSION HAPPENS. See the target
    representation note below.
  Accepts three YAML shapes, in this order: `targets` (spheres with an explicit
    centre and radius), `target_clouds` (one point cloud PER target, each
    reduced by enclosingBall()), and `target_points` (the legacy single-target
    cloud, collapsed to ONE sphere -- it WARNS when it takes this path, since a
    tour over one target has a single stop and anyone who pointed it at
    config/targets.yaml needs to know).
  Does NOT send the algorithm flags: those are planner/vistsp parameters on the
    node, so that an unset message field cannot silently disable an algorithm.
  Prints construction cost, post-2-opt cost and the percentage gain per rule,
    marking the winner -- which is the comparison the four flags exist for.
  Launched by launch/visual_planning_tour.launch, which also exposes the six
    planner/vistsp knobs as roslaunch args (base_locality:=0.0 is the global
    baseline run).

TARGET REPRESENTATIONS -- WHY THERE IS NO "cloud OR sphere" SPLIT IN THE MSGS
  Asked by Stav on 2026-09-09: should target_point_cloud and target_sphere be
  two different structures, propagated through the .msg files and params?
  ANSWER TAKEN: no, because they are not alternatives -- the SPHERE IS DERIVED
  FROM THE CLOUD. Everything below the service already speaks spheres
  (targets_ is std::vector<Ball>, the oracle takes a centre and radius), so the
  sphere is the canonical form and a cloud is an INPUT FORMAT.
  What was done instead:
    * the conversion was extracted into ONE function, enclosingBall() in
      common/Types.h, which computeTargetMES() now calls -- so the planner and
      any client cannot disagree about what sphere a cloud means;
    * PlanVisibilityTour.srv carries spheres only, and clouds are handled at
      the input boundary (the tour client);
    * VisibilityTask.msg and PlanVisibilityPath.srv were NOT TOUCHED, which is
      what guarantees the single-target visibility path cannot break.
  Why the two-structure version was rejected: there are ALREADY two internal
  sources of truth for the target -- targets_ (the coverage query) and
  target_mes_ (several planner helpers) -- and tourCallback() has to set both
  to keep them consistent. Adding two message types would make it three places
  that can disagree, and every consumer would need a rule for "what if both are
  set". The fix direction is to reduce that count, not raise it.
  enclosingBall() is NOT a true minimum enclosing sphere -- it is centred on
  the centroid, exactly as computeTargetMES() always was. Kept deliberately:
  every visibility result in the repo was produced with that definition.

msg/VisibilityTarget.msg  +  srv/PlanVisibilityTour.srv   (NEW 2026-09-09)
  Role: The ROS contract for a VisTSP tour (global_plan step 4).
  Why a SEPARATE service rather than extending PlanVisibilityPath: the tour's
    result -- per-algorithm costs, stop indices, which target each stop
    observes -- does not fit the single-target response, and the single-target
    path serves the TVMP paper and should not change shape for this. Decision
    by Stav, 2026-09-09.
  Why a separate MESSAGE for targets: VisibilityTask carries target_points, a
    point cloud that computeTargetMES() collapses into ONE enclosing sphere.
    VisTSP needs the targets kept apart, since each ball is its own GTSP
    cluster, so VisibilityTarget names a centre and radius per target.
  WHAT vs HOW: the request says what to solve (targets, start joints, planner
    type). How to solve it comes from the planner/vistsp parameters. Stav chose
    parameters over request fields (2026-09-09) because ROS messages have no
    optional fields -- an unset bool arrives as false, so a client that forgot
    them would silently disable all three insertion rules and get a refusal.
    Parameters also match every other knob in the node and need no new
    machinery in experiment_runner, which already sets params before calling.

algorithms/GTSP.h  (~915 lines, NEW 2026-09-09)
  Role: The four E-GTSP heuristics of global_plan step 3 -- nearest, farthest
    and cheapest insertion, plus a 2-opt improvement pass in both the
    fixed-node form (plan 2.5a) and the generalized RP1 form (2.5b).
  Significance: INDEX-ONLY BY DESIGN. It sees a cost matrix, one cluster label
    per node and a depot, and knows nothing about roadmaps, configurations,
    visibility or targets. That is what lets step 6 reuse it unchanged, and it
    is why node splitting (D3) lives in the CoverageTour adapter instead of
    here. It has no dependency on Graph.h or any planner type -- <vector>,
    <limits>, <algorithm>, <cmath>, <iostream> only.
  Contents: GTSPInstance (cost, cluster, clusters, depot, closed);
    GTSPTour (stops, cost, feasible, unserved); InsertionRule enum;
    kGTSPEpsilon, kGTSPRandomizePairOrder, kGTSPPairOrderSeed;
    insertionTour(), twoOpt(), validateTour(), tourCost();
    and a gtsp_detail namespace holding insertionCost(),
    bestInsertionForNode/InCluster(), clusterToTourDistance(), checkInstance(),
    and bestEndpointPair() (RP1's three-term minimisation).
  Why one skeleton: the three insertion rules differ ONLY in the selection step
    and share an identical insertion step, so insertionTour() is a single
    function switched on InsertionRule, exactly as both source documents
    present them. Cheapest has no separate selection at all (plan 2.3).
  Coverage is structural: because the clusters partition the nodes and a tour
    holds one node per cluster, there is NO coverage bookkeeping in this file --
    no uncovered set, no bitmask, no re-validation after a 2-opt move or an RP1
    substitution. checkInstance() verifies the D3 partition rather than
    trusting the builder, since every argument above depends on it.
  The 2-opt enumeration is D6: a plain pair loop over the two removed edges
    (p < q), keeping only pairs whose CYCLIC SEPARATION
    s = min(q-p, |T|-(q-p)) is at least s_min (2 for the fixed-node variant,
    3 for RP1). That separation test IS the correctness condition -- there is
    no runtime guard and no fallback path, and the header says so at length so
    neither gets re-added.
  Why the pair loop rather than a bounded reversed-segment length (Stav,
    2026-09-09): it visits every move exactly once, the segment T[p+1..q] is
    contiguous so the reversal is a plain std::reverse, and index 0 never
    falls inside it. The L-bounded form double-visited moves when |T| is even
    and needed cyclic reversal plus a per-move depot rotation to compensate.
  D7, randomized scan order: the admissible pairs go into a vector that is
    shuffled once per pass, behind the hardcoded kGTSPRandomizePairOrder. Both
    2-opt variants are FIRST-improvement, so the local optimum depends on visit
    order and lexicographic order biases it toward the low-index stops. Order
    cannot affect correctness -- strict decrease per move is untouched. The
    seed is FIXED (kGTSPPairOrderSeed) on purpose: a clock- or
    random_device-seeded shuffle would reintroduce exactly what plan 5.2 exists
    to prevent, non-reproducible tours that make comparing the four algorithms
    meaningless. Vary the seed deliberately for restarts and record it. This
    does NOT replace 5.2's tie-breaking, and it touches 2-opt only -- the three
    insertion constructions stay deterministic greedy.
  Note: stops[0] == depot is a post-condition this file gets for free, NOT
    something the algorithms need -- a cycle has no start and the depot is
    pinned by its singleton cluster. expandTour() (6.1) is the only place a
    real start exists, so any rotation belongs there.
  Gotcha: the cost matrix is a PSEUDOmetric under D3 -- distinct nodes at
    distance 0 -- so every argmin breaks ties deterministically by lowest node
    then lowest position index (plan 5.2), and 2-opt accepts only
    gain > kGTSPEpsilon, never >= 0 (5.1). Without the first the four
    algorithms return different tours on different runs over the same instance;
    without the second the local search cycles forever.
  Fails loudly, never quietly: an open path (closed == false) is refused as
    undesigned, a broken cluster partition is refused, an unreachable cluster
    is named in GTSPTour::unserved with feasible == false, and twoOpt() will
    not improve an infeasible tour.
  Status: written and syntax-checked (g++ -fsyntax-only -std=c++14 -Wall
    -Wextra, clean, both standalone and as an include); NOT yet run or tested -- per the plan's sec. 7 policy,
    anything past a compile check must be proposed first.

  Fails loudly: split_shared_nodes == false is refused as undesigned (O1), as

planners/LocalVisTSP.h  (~300 lines, NEW 2026-09-09)
  Role: global_plan step 4. Drives step 2's coverage query and step 3's GTSP
    heuristics end to end: targets in, motion plan out.
  Significance: NO NEW ALGORITHM. It is the composition of 2 + 3, which is what
    the map's step table always said step 4 was. The sketch in
    local_VisTSP.txt ("G <- LocalVisRRG; GreekTSP(G)") is superseded in both
    halves -- VisRRG dropped 2026-08-26, Greek TSP replaced by the GTSP
    heuristics -- but the composition it described is exactly this.
  "LOCAL" IS A KNOB, NOT A PRECONDITION. Nothing here requires a confined base.
    setBaseLocality(delta) on the PLANNER is what makes a run local; leaving it
    unset runs the same pipeline over the whole environment. BOTH are intended
    uses (Stav, 2026-09-09): local as the per-location unit steps 5-6 will call
    once per base location, and GLOBAL as the BASELINE for the whole
    environment -- the "VisCfgTSP" benchmark of VisTSP_frameworks.txt, whose
    purpose is to measure what the elaborate algorithm's extra layers buy. So
    no code here may assume locality_.enabled.
  Configuration boundary: targets, coverage k, start joints and base locality
    are set ON THE PLANNER, where those setters already live -- duplicating
    them here would be a second source of truth. This class owns only the
    tour-side choices.
  Contents: LocalVisTSPRun (per-rule outcome: construction_cost AND
    improved_cost, two_opt_ran/improved, the tour); LocalVisTSPResult (runs,
    best, path, stop_indices, instance, coverage_incomplete); class LocalVisTSP
    with setUse{Nearest,Farthest,Cheapest}Insertion() / setUseTwoOpt() plus
    getters, setTourParams(), getResult(), solve().
  The four flags are Stav's spec (2026-09-09): one per insertion rule, one for
    2-opt. When 2-opt is on it runs on EVERY enabled rule, not just the winner,
    because "nearest + 2-opt vs farthest + 2-opt" is the comparison wanted and
    it cannot be recovered from a single improved tour. Both costs are stored
    per rule for the same reason. All four default true -- the rules share one
    metric closure, so all three cost barely more than one (plan sec. 4).
  Partial coverage is NOT a failure: planCoverage() returns false when a target
    missed coverage k, but a tour needs only ONE reachable configuration per
    target, so a deficit is still tourable. It is recorded in

    with NO reachable configuration -- is named by buildCoverageTourInstance()

    give two equal consecutive stop indices, an empty leg that is skipped, so a

  Wired into the node 2026-09-09 as the plan_visibility_tour service; see the

    variant (plan 2.5a) is implemented and reachable but not wired to a flag;
    a fifth flag would expose that ablation if it is ever wanted.
  Status: written and syntax-checked (no errors, no warnings from the new
    files); NOT yet run.

components/VisualIK.h
  Role: Visibility-aware inverse kinematics -- the paper's VisIK
    (4_Method.tex, sec:method:vis:ik).
  Significance: The component that turns "this place can see the target" into
    "this joint configuration sees the target".
  Contents: solveIK() (plain MoveIt setFromIK with a ValidityChecker callback);
    solveVisualIK(current_joints, Ball, orientation, out) -- the core: from beam
    half-angle theta and length h it computes the feasible standoff segment
    [a,b] along the view axis (near bound r/tan(theta), far bound h-r), clips
    that segment against a reachability AABB via the slab method, projects the
    current EE position onto it, and then does a bidirectional local search
    along the segment calling IK at each step; overloads for a point list;
    maintainOrientationVisualIK() (keep current EE orientation);
    greedyOrientationVisualIK() (recompute a look-at orientation first).
  TWO GROUPS (2026-08-30): the STATE group (setGroupName) says what a
    configuration vector means -- what seeds are expressed in, what FK is read
    from, what solutions are returned in. The IK group (setIKGroupName) says
    which of those joints the solver may MOVE, defaulting to the state group.
    Set to "manipulator" while a base-locality constraint is active, so a
    solution inherits its seed's base position and cannot leave the disk;
    joints outside the IK group keep their seed values, so inputs and outputs
    stay full state-group vectors either way. checkIK's validity callback
    applies the candidate to the state and reads the FULL state-group vector
    back before collision checking -- with a subgroup, handing ValidityChecker
    the group's own values would pass 6 numbers to a 9-variable group.
    IKGroupGuard (VisibilityPlannerBase.h) is what scopes the restriction: this
    object is shared through PlanningContext, so an unrestored setting would
    leave every later query solving arm-only.
  Known issues, marked in-file with @todo: the search direction/step-size logic
    is flagged WRONG by the author ("dir should be equal to v, step size should
    differ per direction"), and there is a commented-out hard-coded flashlight
    offset. The clipping AABB (-5,-5,0)..(5,5,1.4) is hardcoded here.

data_structures/VisibilityIntegrity.h  (the VI-TREE -- key contribution)
  Role: Implements the Visibility Integrity tree from 4_Method.tex
    (sec:method:visibility:integrity:tree; Algs. vi:tree, vi:tree:recursive,
    vi:tree:query).
  Significance: This is the paper's headline data structure. It answers "which
    regions of the workspace can see this target?" without per-query raycasting.
  Contents:
    - struct VINode: AABB, left/right/parent, is_leaf, height, path_idx string
      (e.g. "0101" for debugging), convexity_score, and
      visible_from_nodes: vector<(VINode*, score)> -- the inverse-visibility list.
    - build(): recursive AABB partition, then ComputeLeafPairwiseVisibility(),
      then ComputeParentVisibilityBottomUp().
    - buildTreeRecursive(): samples S_in inside the box (count scaled down with
      box volume) and S_out in the environment around it (within beam_length),
      uploads the combined set to the GPU as one NxN visibility matrix
      (precomputeGpuMatrix), then computes the VI score as
      |{S_out seen by ALL of S_in}| / |{S_out seen by ANY of S_in}| using the
      checkSeenByAll/Any reduction kernels. Splits on the longest axis while the
      score is below vi_threshold; makes a leaf when the score passes or the box
      shrinks below 0.1 m. Also derives a convexity_score from the same data.
    - ComputeLeafPairwiseVisibility(): one all-pairs GPU batch over leaf centers.
    - ComputeParentVisibilityBottomUp(): a parent's visibility list is the
      INTERSECTION of its children's (sorted-merge), with the score averaged, and
      the relation is written back into the seer's list so queries at any depth
      work. Single-child nodes copy and propagate.
    - query(Eigen::Vector3d, out): descends to the containing leaf, accumulating
      visible_from_nodes from every ancestor on the path.
    - query(Ball, out): the version actually used -- traverses, prunes boxes
      outside the ball, and accumulates a per-seer BALL FRACTION. The covering
      nodes (fully-contained nodes, where recursion stops, plus partially
      intersecting leaves) form a disjoint cover of the ball, so their fractions
      can be summed: each seer's score is the dimensionless fraction of the target
      ball visible from it, in [0,1].
    - query(vector<Ball>, MultiTargetQueryResult&, threshold = 0.8): the
      MULTI-TARGET query (VisTSP subproblem 1, global_plan step 1). Runs the
      single-ball query per target, keeps the seers whose accumulated ball
      fraction is >= threshold, and fills the relation in BOTH directions:
      per_target[t] (regions -> fraction) and region_to_targets (region ->
      target indices). Both are needed because pruning walks regions but
      validates per target. Warns on any target left with no region -- the
      signal that the threshold is stricter than the score distribution allows.
      Per-target fractions are accumulated independently: they may only be
      summed within one target, where the covering nodes form a disjoint cover.
      Seers are returned at ALL tree levels, nested ones included -- collapsing
      to the highest-level node was considered and rejected, because the
      per-node scores record how well each part of a subtree sees the target and
      that resolution would be lost.
      Its first caller (2026-08-30) is VisibilityPlannerBase::
      reportUnseeableTargets, reached through PlanningContext::queryMultiTarget:
      a warning that a target no region sees cannot be covered however long the
      search runs. Advisory only -- a region's score is an aggregate over the
      region, so passing does not promise any single configuration in it sees
      the target.
    - isBuilt(): whether build() has produced a tree. Every query answers
      emptily until it has, which a caller cannot otherwise tell apart from
      "nothing sees the target".
    - Sparse accumulator (accum_ + touched_): the ball query sums each seer's
      fractions through a flat vector indexed by node id rather than a linear
      scan over the output, turning O(covering * list * seers) into
      O(covering * list). Node ids are dense (0 .. num_nodes_-1, sized in
      build()). INVARIANT: accum_ is all zeros between queries -- each query
      resets only the entries in touched_, so cost stays proportional to the
      seers actually hit, and one buffer serves every target of a multi-target
      query. The zero entry doubles as the "not yet credited" marker, which is
      only sound because ball_fraction is strictly positive there.
    - SampleFromVisibilityRegion(Ball, out_point, threshold): rejection sampling
      -- pick a seer, accept it with probability (its ball fraction / the max ball
      fraction over all seers), sample a collision-free point in its box, and
      confirm with a real checkBallBeamVisibility call. The rescale by the max is
      deliberate: raw fractions are usually well below 1 (a seer rarely covers a
      whole target), so using them directly would reject nearly every candidate.
      Dividing by the max preserves the relative ranking -- all that rejection
      sampling needs -- while keeping the best candidate's acceptance rate at 1.
    - Geometry helpers: distSqPointBox, distSqBoxBox, isBoxFullyInBall,
      getBoxVolume/Size, getBallVolume, getIntersectionVolume (raw m^3 of
      box n ball; exact when the box is fully inside, Monte-Carlo otherwise),
      getBallFraction (= getIntersectionVolume / getBallVolume). getBallFraction
      is the SINGLE normalization point -- both the fully-contained and the
      partial case go through it, so scores stay comparable across nodes.
  Gotchas: makeLeaf() APPENDS every leaf to "leaf_boxes.txt" in the process CWD
    (usually ~/.ros) on every build -- a debug/visualization dump that grows
    across runs. intersectsWorkspaceBox() hardcodes the reachable goal AABB
    (-5,-5,0)..(5,5,1.4); intersectsWorkspaceSphere() is an unused alternative
    with a hardcoded 1.2 m sphere at (0.33, 0, 0.33).

data_structures/VisibilityRoadmap.h
  Role: The ALTERNATIVE to the VI-tree: a clustering-based visibility structure.
    Selected by use_visibility_roadmap:=true. This is the "VIR" configuration in
    experiment_runner -- i.e. the Visibility Roadmap BASELINE from
    2_Related_work.tex, not a contribution.
  Significance: Same public query surface as VisibilityIntegrity
    (SampleFromVisibilityRegion, query, isConnectedToTarget), so PlanningContext
    can swap one for the other behind a single boolean.
  Contents: build() = sample N valid workspace points (with optional face
    sampling) -> computeSampleVisibility (all-pairs, GPU with a CPU fallback,
    stored as sorted adjacency lists) -> performClustering() ->
    buildClusterVisibilityGraph() -> build a kNN index over the samples.
    Clustering is greedy: seed on a random point, walk outward by distance, admit
    a point while the incremental VI score (|intersection of visibility sets| /
    |union|) stays >= vi_threshold, stop when the diameter exceeds
    limit_diameter_factor * current diameter. Each cluster gets a centroid and a
    bounding radius. The cluster graph gets an edge when random member pairs are
    mutually visible, weighted by the observed fraction, and is pruned to
    clusters intersecting the goal AABB. query() classifies a point by kNN
    majority vote over cluster labels. Prints extensive cluster statistics and
    dumps "clustered_points.txt".
  Gotcha: goal AABB (-5,-5,0)..(5,5,1.4) is hardcoded again here.

data_structures/VisibilityOracle.h
  Role: All visibility/FoV queries. The CPU-side API over the CUDA kernels.
  Significance: The performance-critical core; every planner decision is
    ultimately an oracle call.
  Contents:
    - Obstacle store as Boost.Geometry Box3D, mirrored to GPU lazily via a
      gpu_dirty_ flag (updateGPUObstacles).
    - isPointInFOV(): the cone test -- transform the target into the sensor
      frame, require +Z half-space, distance <= beam_length, and
      cos(angle) >= cos(beam_angle).
    - isPointInBeam() = isPointInFOV && unoccluded segment.
    - ballOutsideBeam(): closed-form rejection of a ball ENTIRELY outside the
      beam, run first thing inside checkBallBeamVisibility. A ball only
      partially inside is never rejected: for a sensor outside it, the
      directions to its points fill exactly the tangent cone of half-angle
      asin(r/d), and two cones are disjoint only when their axes differ by more
      than the sum of their half-angles. Where it fires, the sampling loop would
      have found nothing in the field of view and returned 0.0, so it changes
      cost and not results. Added for the multi-target coverage queries, which
      test every vertex against every uncovered target.
    - checkBallBeamVisibility(): the central scoring function -- Monte-Carlo
      samples num_samples_ (100) points in the target ball and returns the
      illuminated fraction. Overloads take an Isometry3d pose, a joint vector
      (via the injected FK lambda), or a bare source position (in which case a
      look-at frame is synthesized). NOTE: the GPU batch branch inside this
      function is disabled by `if (false)` -- it always runs the CPU path.
    - computeBatchVisibility(): all-pairs NxN on GPU.
    - checkBatchVisibility(): a list of specific segments on GPU.
    - precomputeGpuMatrix() + checkSeenByAllGPU() / checkSeenByAnyGPU(): upload
      an NxN matrix once and run cheap index-only reductions against it -- this
      is what makes VI-tree construction tractable.
    - VisibilityMethod enum {BF, GPUBF, KDTree}; default GPUBF; KDTree throws.

data_structures/VisibilityOracleGPU.h

data_structures/Graph.h
  Role: Roadmap/tree storage and graph algorithms (namespace-free; class
    GraphManager).
  Contents: Boost adjacency_list<vecS, vecS, undirectedS> with GraphVertex
    {joint_config, ee_pose} and GraphEdge {weight}; addVertex/addEdge (note:
    addEdge inserts BOTH directions into an already-undirected graph, so each
    logical edge appears twice); getVertexConfig/getVertexPose; isEdge;
    shortestPath (Boost Dijkstra + backtracking); inSameComponent (BFS with early
    exit -- used as a cheap pre-check before Dijkstra); countConnectedComponents
    (prints the k largest with a representative config); exportCCMap() (writes
    cc_map.txt: id, joint values, connected-component id -- for offline analysis
    of why PRM failed to connect); printVertexDegrees.
    ADDED 2026-09-09 for step 3: struct SubsetClosure (nodes, cost,
    predecessor) plus metricClosure() and closurePath().
  metricClosure(subset) runs ONE Dijkstra per subset vertex and KEEPS both the
    distance and predecessor maps. It exists because shortestPath() throws
    those maps away after extracting a single path, so a double loop over it
    would run n^2 Dijkstras to recover what n already contain -- and still
    could not answer a second pair from the same source. The retained
    predecessor maps are also exactly what CoverageTour's expandTour() walks.
    It operates on PHYSICAL vertices only and never sees a split node or a
    zero-weight glue edge.
  Gotcha, load-bearing: BGL leaves unreached vertices at
    numeric_limits<double>::max(), which is FINITE. metricClosure() converts
    those to infinity() because the GTSP layer tests reachability with
    `x < infinity()` -- passing max() through would make an unreachable pair
    look like a usable edge of astronomical cost and a tour would be built
    through it and reported feasible. That conversion is the only thing
    preventing it. Note shortestPath() uses the max() comparison directly, so
    the two functions spell the same test differently on purpose.
  metricClosure() rejects a subset containing a duplicate vertex: it would
    create a zero-cost pair between two entries that are the same vertex,
    indistinguishable from -- and corrupting -- D3's split-copy glue.
  Fixed 2026-09-09: the header used std::iota (in countConnectedComponents)
    without including <numeric>, so it was not self-contained and only compiled
    because another header pulled <numeric> in first. Pre-existing; found while
    syntax-checking this file alone, which plan sec. 7.1 requires.

data_structures/NearestNeighbor.h
  Role: kNN over configurations, with a robot-aware metric.
  Significance: Contains a real performance trap -- see below.
  Contents: PointCloud adaptor; RobotStateDistance metric that uses MoveIt
    JointModel::distance per joint and then WEIGHTS the dimensions -- prismatic
    joints (the Husky base translations) by the DOF count, revolute joints by
    (n - i) so proximal arm joints dominate distal ones. This weighting is what
    makes nearest-neighbour queries prefer moving the arm over driving the base.
    Wraps nanoflann KDTreeSingleIndexAdaptor; also provides bruteForceKNN.
  Gotcha: addPoint() DELETES AND REBUILDS the entire kd-tree on every insertion,
    making roadmap construction O(n^2 log n). This is the most likely target if
    PRM build time needs to come down (cf. commit "trying to make NN faster").

src/visual_planning_node.cpp
  Role: The main ROS service node -- the production entry point.
  Contents: class VisualPlanningNode wraps a PlanningSceneMonitor, one shared
    PlanningContext, and a swappable VisibilityPlannerBase, and advertises
    "plan_visibility_path" and, since 2026-09-09, "plan_visibility_tour".
    - loadStaticConfig(): reads every parameter from the PRIVATE namespace
      (planner_config.yaml). Context-level values go straight to ctx_;
      planner-level ones (RRT/PRM params, time cap, snap_fov_on_insert,
      snap_fov_on_scan) are RETAINED as members so a rebuilt planner can be
      configured identically. First calls rejectRetiredParams(), which REFUSES
      TO START if a config still sets a renamed parameter (currently
      use_visual_ik -> snap_fov_on_insert): ROS reports nothing for a parameter
      nobody reads, so the run would silently take the new default and, for this
      one, benchmark the wrong algorithm.
    - refreshPlanningScene() (NEW 2026-09-16): calls
      psm_->requestPlanningSceneState() at startup and at the top of BOTH
      service callbacks. The monitor is a SUBSCRIBER, so it only ever learned
      about geometry published after it connected; a scene loaded before the
      node started was invisible and the node then planned in an empty world
      without saying so. That is what made readme.txt's "the scene must be
      loaded AFTER the service is launched" load-bearing -- and getting it wrong
      produced paths through walls rather than an error. MUST be called BEFORE
      taking LockedPlanningSceneRO: the request takes the scene's write lock, so
      calling it while holding the read lock deadlocks. One /get_planning_scene
      round trip against a query capped at planner/time_cap seconds, so it is
      unconditional rather than a knob.
    - rebuildPlanner(scene, mode): builds the planner named by mode on the
      existing context and attachScene()s it. Cheap -- no VI-tree rebuild.
      Returns false on an unknown mode; the constructor treats that as fatal and
      a request treats it as a failed request. There is deliberately NO fallback
      to a default planner.
    - updatePlannerParams(): on EVERY service call, re-reads five switches from
      the GLOBAL namespace (/planner/snap_fov_on_insert,
      /planner/snap_fov_on_scan, /planner/use_visibility_integrity,
      /planner/use_visibility_roadmap, /planner/enable_shortcutting, planner/mode)
      and sets params_changed_ if any differ. This is the mechanism
      experiment_runner uses to switch algorithms without restarting the node.
    - preparePlanner(mode, ls, mode_out) + applyStartJoints(): EXTRACTED
      2026-09-09 when the tour service was added, behaviour unchanged. They hold
      the setup both callbacks need -- param refresh, mode resolution, context
      re-init, planner swap, start configuration. Extracted rather than copied
      because two handlers each carrying their own copy would drift and one
      service would quietly plan with stale parameters.
    - loadTourConfig(): reads the planner/vistsp parameters (the four algorithm
      flags, coverage, base_locality_radius). Called from loadStaticConfig() and
      AGAIN at the top of every tour request, so a sweep can change the
      algorithm set between calls without restarting the node. None of them
      forces a planner rebuild.
    - tourCallback(): the VisTSP entry point (global_plan step 4). Converts the
      request's target balls, calls setTargets() AND computeTargetMES() over the
      centres (the coverage query uses setTargets(), but several planner helpers
      still read target_mes_, which would otherwise hold whatever a previous
      single-target request left there), applies coverage and locality, then
      runs LocalVisTSP and fills the response. Reports the per-rule costs even
      on failure, since a failure after some rules succeeded is still
      informative.
    - planCallback(): resolves the mode (req.planner_type overrides the param
      server for that call only); if the CONTEXT is uninitialized OR params
      changed, resets the planner and re-snapshots the scene (this is what
      triggers the VI-tree rebuild); rebuilds the PLANNER if the mode differs
      from the one built or a construction-time flag changed; then computes the
      target MES and start joints -- in that order, because both are per-run
      state that a rebuild would discard -- calls plan(), and packs the result
      into a JointTrajectory with the group's active joint names.
    - main(): RobotModelLoader + PlanningSceneMonitor with scene/world/state
      monitors, AsyncSpinner(2).

  Contents:

1. "whole_robot" vs "manipulator": the planning group was switched from the UR5
   alone to the full 9-DOF mobile manipulator. The old value survives as
   commented-out lines in the planners/ headers, ValidityChecker.h, NearestNeighbor.h,
   visual_ik_server.cpp, visual_ik_client.cpp, visual_planning_client.cpp.
   ValidityChecker::isValid() still hardcodes "whole_robot" in its
   getJointModelGroup call rather than using group_name_.
2. The reachable/goal AABB (-5,-5,0)..(5,5,1.4) is hardcoded in THREE places:
   VisibilityIntegrity::intersectsWorkspaceBox, VisibilityRoadmap::
   buildClusterVisibilityGraph, and VisualIK::solveVisualIK. Changing the
   environment means changing all three.
3. Debug artifacts are written to the process CWD (~/.ros when launched by
   roslaunch): leaf_boxes.txt (appended, grows unboundedly), clustered_points.txt,
   cc_map.txt.
4. The CUDA arch flag is pinned to sm_89 in CMakeLists.txt.
5. VisibilityOracle::checkBallBeamVisibility's GPU branch is dead code
   (`if (false)`); ball visibility scoring is CPU-bound.
6. The PRM roadmap deliberately PERSISTS across service calls; only a param
   change or scene change resets it. Timing numbers only make sense in that light.
7. TARGET ROBOTS ARE EXACTLY TWO (Stav, 2026-08-30): the SIMULATED mobile UR5,
   whose base x/y are prismatic joints anchored to the centre of the
   environment, and the REAL Husky + UR5. Nothing else -- no other robot,
   simulated or otherwise, needs to be supported. Generality is explicitly worth
   trading away for simpler code here. Concretely, the first two variables of
   the planning group ARE the base translation, and code may rely on it.
   Where the base is gets asked through PlanningContext::basePosition() so that
   the real Husky, which will report its base from localization rather than
   from a joint value, changes one method (or backs it with a ROS service)
   instead of every caller.
   OPEN RISK on the real Husky, flagged by Stav as untried (2026-08-30), and
   UNVERIFIED against their setup:
   (a) Getting the base position may not need new code at all. If the Husky's
       base is a PLANAR VIRTUAL JOINT (map -> base_link) inside the planning
       group, q[0]/q[1] stay the base translation and PlanningSceneMonitor
       already fills the current state from TF; the work is then SRDF plus a
       localization source, not C++. basePosition() only has to change if the
       base ends up OUTSIDE the planning group.
   (b) The harder problem is that a Husky is DIFFERENTIAL-DRIVE while the
       simulated base is two prismatic joints, which slide sideways. Every base
       path this code plans is therefore a relaxation the real robot may not be
       able to execute. Under a small locality disk the base barely moves so it
       is minor; for the global tour over base locations (global_plan step 6) it
       is not, and nothing in the repo addresses it yet.
8. ONE PLANNER PER REGION is the contract for the VisTSP pipeline (Stav,
   2026-08-30). Whenever a graph is needed -- local or global -- construct a
   planner and take its graph; each local region gets its own, because each
   region's tour is computed from its own graph. This is why the base-locality
   constraint needs no guard against a roadmap built under a different disk:
   there is no shared mutating roadmap to protect. Reusing one planner with a
   LARGER delta is legitimate, its vertices all still being inside, and
   shrinking one is the caller's business -- recordVisibleTargets tests
   inLocality on the vertex it is given, so the answer stays correct either way.
   A freshly constructed planner must be attachScene()d before it can plan.

GTSP_heuristic_algorithms.pdf
  Role: Source for global_plan step 3. Two scanned pages (632-633) of "The
    Traveling Salesman Problem and its Variations", sec. 2.5 "Heuristic
    algorithms" and the head of sec. 2.6, covering the Fischetti, Salazar and
    Toth heuristics for GTSP / E-GTSP.
  Contents: how to adapt farthest insertion (and, "in a similar way", nearest
    and cheapest insertion) to E-GTSP -- cluster distance
    d_hk = min{c_ij : i in C_h, j in C_k}; seed from the two mutually farthest
    clusters; per iteration select the uncovered cluster farthest from the
    partial tour, then insert the node v of it minimising
    c_iv + c_vj - c_ij over consecutive tour pairs (i, j). Then two tour
    IMPROVEMENT procedures: RP1, a generalized 2-opt (and 3-opt) that re-picks
    which node is used in the clusters at the ends of the changed edges, via
    two independent 3-term minimisations, O(n^2) over all cluster pairs; and
    RP2, which finds the OPTIMAL node choice for a FIXED cluster sequence by
    shortest paths through a layered acyclic network of m+1 layers, and which
    yields an O((m-1)! n^3) exact algorithm when run over all sequences.
  Note: E-GTSP is the variant where every cluster is visited EXACTLY once. The
    scan's OCR is poor -- subscripts and formulas are mangled -- so read the
    formulas from the plan file's reconstruction rather than from a text dump.

  Role: Sources for global_plan step 3. Saved pages from Georgia Tech's TSP

    (Rosenkrantz, Stearns and Lewis 1974) that the PDF adapts to E-GTSP.

GTSP_implementation_plan.txt
  Role: Implementation plan for global_plan step 3 (the four GTSP algorithms).
    DESIGN SETTLED 2026-09-08; no code written yet. Read sec. 8 first -- it
    records Stav's decisions and is the authority on them.
  THE SIX DECISIONS (sec. 8, restated at the top of the file as D1-D6):
    D1 the tour is a CYCLE; D2 every run is seeded from the DEPOT (= the start
    configuration), so the PDF's unrooted "two mutually farthest clusters" seed
    and the whole d_hk cluster-distance table are dropped; D3 NODE SPLITTING --
    a configuration seeing several targets becomes one node per target, the
    copies joined by a ZERO-WEIGHT clique, so the clusters PARTITION the nodes
    and the problem is textbook E-GTSP; D4 costs are roadmap Dijkstra
    distances; D5 2-opt is the PDF's generalized RP1 form, which re-picks which
    node of the cluster is used at the ends of the changed edges; D6 2-opt is
    enumerated over PAIRS OF REMOVED EDGES (p < q), keeping only those whose
    CYCLIC SEPARATION s = min(q-p, |T|-(q-p)) is at least s_min -- 2 for the
    fixed-node variant, 3 for RP1. That is how RP1's independence requirement
    is enforced: part of the enumeration, not a per-move guard, and no
    fallback path.
  WHY D3 IS THE CENTRAL ONE: recordVisibleTargets() credits a vertex to every
    target it sees, so goals[] as delivered has OVERLAPPING clusters, which
    textbook E-GTSP forbids. Splitting makes coverage STRUCTURAL (one node per
    cluster always covers everything, so there is no coverage bookkeeping, no
    re-validation after a 2-opt move, no redundant-stop pass) and makes "which
    cluster does this stop serve" unambiguous, which is what RP1 needs to
    define its replacement candidates. Sec. 2.4 PROVES the zero-weight glue
    makes all three insertion rules visit the copies in succession (insertion
    cost beside a placed copy is exactly 0, and no insertion cost is ever
    negative), so nothing is lost against exploiting the overlap directly;
    farthest insertion merely defers them to the end of construction.
  Contents: (0) where the code goes -- a three-way split rather than all of it
    in GraphManager: a metricClosure() primitive in Graph.h, the four
    algorithms in a new algorithms/GTSP.h against an index-only instance (cost
    matrix + one cluster id per node + depot, no Boost/MoveIt/ROS, so step 6
    reuses them unchanged), and a planners/CoverageTour.h adapter that is where
    splitting happens -- the split nodes and zero-weight edges must never enter
    GraphManager, which VisPRM and VisRRT plan on; (1) the instance, the cost
    model and its consequences (no leg can be infeasible, so the old
    "shortcut-or-RRT" fallback is not a feasibility requirement), splitting,
    the depot as a singleton cluster, and dropping goals unreachable from the
    root for free out of the depot's Dijkstra sweep; (2) the four algorithms
    over one shared skeleton, plus the succession proof and the derivation of
    RP1's s_min = 3 SEPARATION (the PDF's two-edge decomposition is invalid
    exactly when the two removed edges are within cyclic distance 2, so those
    pairs are not enumerated at all -- 2.5a covers them and runs first);
    (3) the API; (4) complexity -- splitting adds NO Dijkstras, the closure is
    computed over PHYSICAL vertices and copies are rows reached by lookup;
    (5) degenerate-metric hazards splitting introduces (strict-improvement-only
    2-opt, deterministic tie-breaking, never infer identity from a zero cost);
    (6) tour -> motion plan, the per-leg-only smoothing rule, and 6.2 Stav's
    planned RRT shortcut augmentation; (7) the VERIFICATION POLICY;
    (8) decisions + two open items; (9) source material kept for reference,
    including RP2, which is explicitly out of scope.
  VERIFICATION POLICY (sec. 7, Stav 2026-09-08): code is NOT to be verified
    immediately after being written. A syntax-only g++ check in the
    ubuntu1804-husky container is welcome unprompted; anything beyond it (test
    executables, brute-force comparisons, running the pipeline) must be
    proposed and agreed FIRST. Sec. 7.2 keeps the verification material as a
    menu for when it is wanted, not as a step to carry out.
  STILL OPEN: O1 the split-OFF mode is undesigned, so the adapter must FAIL
    LOUDLY when split_shared_nodes is false rather than run E-GTSP on
    overlapping clusters. O2 is DEFERRED, not open: Stav
    postponed 6.2's RRT shortcut augmentation on 2026-09-09 and may pick it up
    later, so its scope question (leg-local vs. roadmap augmentation and a
    re-solve) is deliberately unanswered. Nothing waits on it -- expandTour()
    already returns a valid motion plan, since every leg is a roadmap path and
    shortcutting was only ever an improvement, never a feasibility step.
  O3 RESOLVED 2026-09-09 -> D6, the sixth shaping decision. RP1's independence
    condition is now an ENUMERATION BOUND, not a per-move guard: 2-opt is
    enumerated over pairs of removed edges (p < q) whose cyclic separation
    s = min(q-p, |T|-(q-p)) is at least s_min = 2 for the fixed-node variant
    (2.5a) and 3 for RP1 (2.5b). The anchors of RP1's two minimisations collide
    exactly when the reversed-segment length L is in {1, 2, |T|-2, |T|-1},
    which -- since L and |T|-L are the same move -- is precisely s <= 2, so
    s_min = 3 is exactly the condition and no runtime guard or fallback path
    exists. Stav's call was to SKIP those moves rather than price them with
    2.5a's gain, since 2.5a covers them and runs first. He also chose the pair
    enumeration over the reversed-segment-length bound first drafted here
    (2026-09-09): it visits every move once, needs no cyclic reversal, and
    leaves index 0 alone, where the bounded form did none of those. Two conditions from the
    earlier draft were rejected and are recorded in 2.5b so they are not
    re-added: "share a cluster" is vacuous under D3, "share a physical vertex"
    needs no guard. Consequence: RP1's move set is non-empty only for |T| >= 6,
    so it does nothing below 5 targets and 2.5a alone improves the tour there.
    The 6.1 sub-question was settled with it -- non-adjacent copies of one
    physical vertex are ACCEPTED as two real visits, since merging them needs a
    relocation (Or-opt) move 2-opt cannot reach. twoOpt(generalized=true) is
    unblocked and the whole plan is now free of open correctness items.
  Supersedes: the "TSP Greek Alg" half of local_VisTSP.txt and the unapproved
    2026-09-01 MST/post-order/shortcut proposal.

HOW THE PIECES RELATE
---------------------
The paper (Part 2, Group A) defines the primitives -- the VI measure, the VI-tree,
VisIK, and the VisPRM/VisRRT planners for single-goal TVMP. Part 1 (the repo) is
their implementation on the Husky + UR5, together with the VIR baseline and the
benchmark harness that produced 5_Experiments.tex. The VisTSP notes (Part 2,
Group B) reuse those same primitives -- above all the VI-tree query and VisIK --
to build multi-target coverage: regions from the VI-tree, base locations covering
those regions, a global tour over locations, and local visibility tours at each
stop. global_plan.txt sequences that into 6 build steps, of which only step 1 is
written (Part 3). The reuse is now literal rather than conceptual: as of
2026-08-26 the local coverage stage is not a new planner but a multi-target,
k-coverage, base-locality-constrained query mode ON VisRRT and VisPRM
themselves.
